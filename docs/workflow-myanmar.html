QuickFix Project

အိမ်သုံးနှင့် နေ့စဉ်ဝန်ဆောင်မှုများကို Customer နှင့် Service Provider တို့ ချိတ်ဆက်ပေးသော ဝဘ်အက်ပလီကေးရှင်း။ ဤစာတမ်းတွင် စနစ်၏ရည်ရွယ်ချက်၊ အသုံးပြုသူအခန်းကဏ္ဍ၊ အဓိကလုပ်ငန်းစဉ်များနှင့် နည်းပညာဖွဲ့စည်းပုံကို တင်ပြရှင်းပြနိုင်ရန် အသေးစိတ်ဖော်ပြထားသည်။

မာတိကာ

စီမံကိန်းအကျဉ်းအသုံးပြုသူများအဓိက WorkflowModule များနည်းပညာDatabaseDemo အစီအစဉ်မေးခွန်းနှင့်အဖြေ

၁။ စီမံကိန်းအကျဉ်း

QuickFix သည် ဖောက်သည်တစ်ဦးက လိုအပ်သော ဝန်ဆောင်မှုကို ရှာဖွေ၊ အလုပ်အပ်နှံ၊ အခြေအနေကြည့်ရှု၊ ငွေပေးချေပြီး အလုပ်ပြီးနောက် သုံးသပ်ချက်ပေးနိုင်စေသည်။ Provider ဘက်တွင် အလုပ်တောင်းဆိုမှုများကို လက်ခံ/ငြင်းပယ်ခြင်း၊ အလုပ်အဆင့်တစ်ဆင့်ချင်း ပြောင်းခြင်း၊ ငွေလက်ခံမှုနှင့် ဝင်ငွေကို စီမံခြင်းတို့ ပြုလုပ်နိုင်သည်။ Admin ဘက်ကတော့ စာရင်းသွင်းအသုံးပြုသူများနှင့် စနစ်အတွင်းရှိ ဝန်ဆောင်မှုအချက်အလက်များကို စီမံခန့်ခွဲနိုင်သည်။

တင်ပြရာတွင် တစ်ကြောင်းတည်းဖြင့်
“QuickFix က Customer တွေကို သင့်တော်တဲ့ ဝန်ဆောင်မှုပေးသူနဲ့ ချိတ်ဆက်ပေးပြီး booking ကနေ payment၊ review အထိ လုပ်ငန်းစဉ်ကို တစ်နေရာတည်းမှာ စီမံပေးတဲ့ platform ဖြစ်ပါတယ်။”

ဖြေရှင်းပေးသည့်အရာများ

  • ဖုန်းဆက်ရှာဖွေမှုအစား ဝန်ဆောင်မှုနှင့် Provider ကို စနစ်တကျကြည့်ရှုနိုင်ခြင်း။
  • Booking ၏အခြေအနေကို မှတ်တမ်းနှင့်တကွ လိုက်ကြည့်နိုင်ခြင်း။
  • ဖောက်သည်နှင့် Provider တို့အကြား စာတိုပေးပို့နိုင်ခြင်း။
  • ငွေပေးချေမှု၊ ငွေပြန်အမ်းမှုနှင့် review အချက်အလက်များကို ချိတ်ဆက်သိမ်းဆည်းခြင်း။

၂။ အသုံးပြုသူအခန်းကဏ္ဍ

အခန်းကဏ္ဍအဓိကတာဝန်ဝင်ရောက်နိုင်သော လုပ်ဆောင်ချက်များ
Customerဝန်ဆောင်မှုလိုအပ်သူဝန်ဆောင်မှုရှာရန်၊ Booking တင်ရန်၊ Booking နှင့် payment အခြေအနေကြည့်ရန်၊ Provider နှင့် chat လုပ်ရန်၊ အလုပ်ပြီးလျှင် review ပေးရန်။
Providerဝန်ဆောင်မှုပေးသူProfile နှင့် ဝန်ဆောင်မှုများသတ်မှတ်ရန်၊ availability ပြောင်းရန်၊ Booking ကိုလက်ခံ/ငြင်းပယ်ရန်၊ အလုပ်အဆင့်များတင်ရန်၊ payment slip စစ်ဆေးရန်၊ ဝင်ငွေနှင့် review ကြည့်ရန်။
Admin / Superadminစနစ်စီမံခန့်ခွဲသူCustomer၊ Provider၊ Booking၊ service၊ category၊ city၊ service area နှင့် payment များကို စီမံကြည့်ရှုရန်။ Provider approval ကို ဆုံးဖြတ်ရန်။

အကောင့်များအားလုံးတွင် အခြေခံအချက်အလက်များကို users ဇယား၌ သိမ်းထားပြီး အခန်းကဏ္ဍအလိုက် customers၊ providers သို့မဟုတ် admins profile နှင့် ဆက်စပ်ထားသည်။ Route များတွင် auth နှင့် role middleware သုံးထားသောကြောင့် login ဝင်ထားသူနှင့် သတ်မှတ်အခန်းကဏ္ဍကို စစ်ပြီးမှ သက်ဆိုင်ရာစာမျက်နှာကို ဝင်ခွင့်ပေးသည်။

၃။ အဓိကလုပ်ငန်းစဉ် (End-to-end Workflow)

အဆင့် A — အကောင့်ဖွင့်ခြင်းနှင့် ဝင်ရောက်ခြင်း

  1. အသုံးပြုသူက အမည်၊ email၊ ဖုန်း၊ password နှင့် Customer သို့မဟုတ် Provider အခန်းကဏ္ဍကို ဖြည့်သည်။
  2. Server က လိုအပ်သော field များ၊ email မထပ်မှု၊ password အတည်ပြုမှုနှင့် role ကို စစ်ဆေးသည်။ Password ကို hash လုပ်ပြီး သိမ်းသည်။
  3. Provider ဖြစ်ပါက မြို့/ဧရိယာ၊ အတွေ့အကြုံနှင့် ဝန်ဆောင်မှုများကို profile နှင့်ချိတ်သည်။ စာရင်းသွင်းချိန်တွင် approval အခြေအနေ pending ဖြစ်သည်။
  4. Provider ကို Admin က အတည်ပြုပြီးမှ login ဝင်နိုင်သည်။ Login အောင်မြင်လျှင် role အလိုက် customer၊ provider သို့မဟုတ် admin dashboard သို့ပို့သည်။

အဆင့် B — Customer က Booking တင်ခြင်း

  1. Customer က active category နှင့် service များကို browse လုပ်ပြီး လိုချင်သော service ကို ရွေးသည်။
  2. Booking form တွင် service တစ်ခု/တစ်ခုထက်ပို၊ မြို့နှင့် service area၊ Provider၊ ASAP သို့မဟုတ် အချိန်ချိန်း booking အမျိုးအစား၊ လိပ်စာ၊ မှတ်ချက်တို့ကို ထည့်သည်။ ပြဿနာဓာတ်ပုံကို optional အဖြစ် တင်နိုင်သည်။
  3. Server က service၊ city၊ area၊ provider ဆက်စပ်မှုနှင့် booking အချက်အလက်များကို validate လုပ်ပြီး စုစုပေါင်းပမာဏနှင့် ကြိုတင်ပေးချေ/ကျန်ငွေကို တွက်ချက်သည့် flow ကို ဆောင်ရွက်သည်။
  4. Database transaction အတွင်း Booking၊ Payment နှင့် ပထမဆုံး status history ကို ဖန်တီးသည်။ Transaction သည် ဆက်စပ်ရေးသားမှုများကို တစ်စုတစ်စည်းတည်း သိမ်းရန် အသုံးပြုသည်။
  5. Provider ထံ Booking အသိပေးချက်သွားပြီး Booking သည် Provider ၏တုံ့ပြန်မှုကို စောင့်နေသည်။

အဆင့် C — Provider ၏တုံ့ပြန်မှု

PendingBooking တင်ပြီး Provider ၏ဆုံးဖြတ်ချက်ကို စောင့်သည်။
AcceptedProvider လက်ခံလျှင် ကြိုတင်ငွေပေးချေမှုအဆင့်သို့ သွားသည်။
Rejected / CancelledProvider ငြင်းပယ်ခြင်း သို့မဟုတ် ခွင့်ပြုထားသော အခြေအနေတွင် ပယ်ဖျက်ခြင်း။
Timeoutသတ်မှတ်တုံ့ပြန်ချိန် ကျော်လွန်ပါက အချိန်ကုန်အခြေအနေကို မှတ်တမ်းတင်နိုင်သည်။

လက်ခံ/ငြင်းပယ်ခြင်းမတိုင်မီ စနစ်က Booking ၏ လက်ရှိအခြေအနေကို စစ်သည်။ ခွင့်မပြုသောအခြေအနေမှ ထပ်မံပြောင်းလဲမှု မဖြစ်စေရန် ထိန်းထားသည်။ အခြေအနေပြောင်းတိုင်း booking_status_history တွင် မှတ်တမ်းတင်ပြီး သက်ဆိုင်ရာ Customer ကို notification ပို့သည်။

အဆင့် D — ကြိုတင်ငွေနှင့် အလုပ်ဆောင်ရွက်မှု

  1. Provider လက်ခံပြီးနောက် Customer က ကြိုတင်ငွေပေးချေမှုအတွက် payment method နှင့် slip အချက်အလက်ကို တင်သွင်းသည်။
  2. ဤ codebase တွင် Provider က payment slip ကို စစ်ဆေးအတည်ပြု သို့မဟုတ် အကြောင်းပြချက်နှင့်အတူ ငြင်းပယ်သည့် လုပ်ငန်းစဉ်ရှိသည်။ စနစ်တွင် ပြင်ပ payment gateway တစ်ခုကို ချိတ်ထားသည်ဟု မဖော်ပြထားပါ။
  3. ကြိုတင်ငွေ အတည်ပြုပြီးနောက် Provider သည် အလုပ်အဆင့်ကို accepted → on_the_way → arrived → in_progress အစဉ်အတိုင်း တိုးမြှင့်သည်။
  4. ဝန်ဆောင်မှုပြီးဆုံးသောအခါ Provider က complete လုပ်ဆောင်ချက်ကို ပြုလုပ်ပြီး Booking အခြေအနေသည် completed ဖြစ်သွားသည်။ ကျန်ငွေပေးချေမှုအဆင့်ကို ဖွင့်ပေးပြီး Customer က နောက်ဆုံးငွေပေးချေမှုအထောက်အထားကို တင်သွင်းသည်။
  5. Provider သည် နောက်ဆုံးငွေပေးချေမှုကို စစ်ဆေးအတည်ပြုနိုင်သလို ငြင်းပယ်နိုင်သည်။ ကြိုတင်ငွေနှင့် နောက်ဆုံးငွေ အတည်ပြုမှုကို Payment record တွင် သီးခြားစီ သိမ်းသည်။
အခြေအနေအစဉ်ကို သတိပြုရန်
Booking status နှင့် payment status သည် မတူညီသော field များဖြစ်သည်။ ဥပမာ Booking သည် completed ဖြစ်နိုင်သော်လည်း final payment သည် စစ်ဆေးဆဲဖြစ်နိုင်သည်။

အဆင့် E — ပယ်ဖျက်ခြင်းနှင့် refund

ပယ်ဖျက်သည့်သူ၊ အကြောင်းပြချက်နှင့် အချိန်ကို Booking တွင် သိမ်းသည်။ ကြိုတင်ငွေကို အတည်ပြုပြီးသားဖြစ်ပါက refund လိုအပ်မှုကို payment record နှင့် refund status ဖြင့် ကိုင်တွယ်နိုင်သည်။ Provider က refund အထောက်အထားတင်ပြီး Customer က အတည်ပြု/ပြန်လည်တုံ့ပြန်သည့် field များလည်း ပါရှိသည်။ ခွင့်ပြုနိုင်သည့် ပယ်ဖျက်မှုအဆင့်များကို controller က စစ်ဆေးသည်။

အဆင့် F — ပြီးဆုံးပြီးနောက်

Customer က ပြီးဆုံးသော Booking အတွက် rating နှင့် review ပေးသည်။ Provider သည် ရရှိထားသော review များကို ကြည့်နိုင်သည်။ Booking ၏ payment၊ chat၊ review နှင့် status history တို့က သက်ဆိုင်ရာ Booking နှင့် ချိတ်ဆက်ထားသည်။

Moduleအလုပ်လုပ်ပုံအဓိကဖိုင်/နေရာ

၅။ နည်းပညာနှင့် Architecture

  • Backend: PHP 8.2 နှင့် Laravel 12။
  • Frontend: Laravel Blade၊ HTML/CSS၊ JavaScript၊ Bootstrap/Tailwind နှင့် Vite build tool များ။
  • Database: Laravel migration များဖြင့် schema ကို သတ်မှတ်ထားသည်။ မည်သည့် database ကို အသုံးပြုမည်ကို project ၏ local .env setting က ဆုံးဖြတ်သည်။ Secret ပါနိုင်သဖြင့် .env တန်ဖိုးများကို မျှဝေမပြသင့်ပါ။
  • Request flow: Browser → routes/web.php → authentication/role middleware → Controller (validation + business rule) → Eloquent Model/Database → Blade view သို့မဟုတ် JSON response။
RouteURL နှင့် HTTP method ကို controller action သို့ ချိတ်သည်။
MiddlewareLogin နှင့် role ကို စစ်ဆေးသည်။
ControllerInput စစ်ပြီး လုပ်ငန်းစည်းမျဉ်းကို ဆောင်ရွက်သည်။
ModelDatabase relation နှင့် query များကို ကိုင်တွယ်သည်။
Viewရလဒ်ကို အသုံးပြုသူမြင်နိုင်သော စာမျက်နှာအဖြစ် ပြသည်။

လုံခြုံရေး/တိကျမှုဆိုင်ရာ ရှင်းပြချက်: Laravel authentication နှင့် session ကို သုံးသည်။ Form input များကို validation လုပ်ထားပြီး password ကို hash လုပ်သည်။ Role route များကို middleware ဖြင့် ကာကွယ်ထားသည်။ အရေးကြီးသော multi-record write များတွင် database transaction ကို သုံးထားသည်။

၆။ အဓိက Database Entity များ

ဇယား/Modelသိမ်းဆည်းသည့်အချက်အလက်နှင့် ဆက်စပ်မှု
usersအကောင့်၊ login နှင့် role ၏ အခြေခံအချက်အလက်။ Customer/Provider/Admin profile များ၏ မိခင်အကောင့်။
customers, providers, adminsRole သီးသန့် profile အချက်အလက်များ။ Provider တွင် approval၊ availability၊ service area၊ experience စသည် ပါဝင်သည်။
service_categories, servicesဝန်ဆောင်မှုအမျိုးအစားနှင့် ရွေးချယ်နိုင်သော service များ။ Provider-service ချိတ်ဆက်မှုအတွက် pivot ဇယားရှိသည်။
cities, service_areasတည်နေရာနှင့် ဝန်ဆောင်မှုပေးနိုင်သည့် နယ်မြေများ။ Area သည် City နှင့် ဆက်စပ်သည်။
bookingsCustomer၊ Provider၊ နယ်မြေ၊ ရွေးထားသော service များ (JSON)၊ အချိန်၊ လိပ်စာ၊ စုစုပေါင်းနှင့် လက်ရှိ status။
paymentsBooking ၏ကြိုတင်/နောက်ဆုံးငွေ၊ slip၊ verification၊ rejection နှင့် refund အခြေအနေများ။
booking_status_historyBooking status ပြောင်းလဲမှု၊ ပြောင်းလဲသူနှင့် အချိန်ကို ခြေရာခံသည်။
chats, reviews, notificationsBooking ဆိုင်ရာစကားပြောမှတ်တမ်း၊ Customer အကဲဖြတ်ချက်နှင့် အသုံးပြုသူထံပို့သော အသိပေးချက်များ။

Migration ဖိုင်များသည် database/migrations ထဲတွင်ရှိပြီး schema ပြောင်းလဲမှုကို အချိန်လိုက် မှတ်တမ်းတင်သည်။ Model များရှိ Eloquent relationship များက Booking မှ Customer/Provider/Payment/Review/Chat/History သို့ ဆက်သွယ်နိုင်စေသည်။

၇။ တင်ပြပွဲအတွက် Demo အစီအစဉ်

  1. Project ရည်ရွယ်ချက်နှင့် Customer–Provider–Admin အခန်းကဏ္ဍ ၃ မျိုးကို မိတ်ဆက်ပါ။
  2. Customer အဖြစ် service ရှာပြီး booking form တွင် service၊ တည်နေရာ၊ အချိန်နှင့် မှတ်ချက်ဖြည့်ပါ။
  3. Provider dashboard တွင် တောင်းဆိုမှုကို လက်ခံပြီး booking detail/status history ကို ပြပါ။
  4. Payment စာမျက်နှာတွင် prepayment နှင့် final payment ကို သီးခြားစီ စစ်ဆေးကြောင်း ရှင်းပြပါ။
  5. Provider ၏ အလုပ်အဆင့်ပြောင်းလဲမှု၊ Customer notification၊ chat တို့ကို ပြပါ။
  6. အလုပ်ပြီးနောက် review နှင့် Admin ၏ data management/Provider approval ကို အဆုံးသတ်အဖြစ် ပြပါ။

Demo အတွင်း အမှန်တကယ်ငွေပေးချေမှုလုပ်မည်ဆိုပါက သတ်မှတ်ထားသော development/test data ကိုသာ အသုံးပြုပါ။

၈။ အခြားသူများ မေးနိုင်သော မေးခွန်းများနှင့် အဖြေများ

ဒီ project က ဘာပြဿနာကို ဖြေရှင်းပေးတာလဲ?

Customer က လိုအပ်သော service နှင့် Provider ကို ရှာပြီး တောင်းဆိုမှုတင်နိုင်စေတယ်။ Provider က အလုပ်ကို စနစ်တကျတုံ့ပြန်နိုင်ပြီး booking၊ payment၊ communication နဲ့ review မှတ်တမ်းတွေကို တစ်နေရာမှာ ချိတ်ဆက်ပေးတယ်။

အသုံးပြုသူ role များကို ဘယ်လိုခွဲထားသလဲ?

users.role ဖြင့် customer၊ provider၊ admin သို့မဟုတ် superadmin အဖြစ် ခွဲထားတယ်။ Route တွေမှာ auth နဲ့ ကိုယ်ပိုင် role middleware ကို အသုံးပြုပြီး ခွင့်ပြုထားတဲ့ role သာ ဝင်နိုင်တယ်။

Provider တစ်ယောက်က စာရင်းသွင်းပြီးတာနဲ့ အလုပ်လက်ခံနိုင်သလား?

မရပါ။ Registration အချိန် approval status က pending ဖြစ်ပြီး Admin အတည်ပြုမှ Provider အဖြစ် ဝင်ရောက်လုပ်ဆောင်နိုင်တယ်။

Booking တင်ပြီးရင် ဘာတွေဖြစ်သလဲ?

Booking နဲ့ payment ဆိုင်ရာ record တွေကို ဖန်တီးတယ်၊ status history မှတ်တမ်းတင်တယ်၊ Provider ကို အသိပေးတယ်။ Provider က လက်ခံ/ငြင်းပယ်ပြီး လက်ခံခဲ့ရင် ကြိုတင်ငွေနဲ့ အလုပ်ဆောင်ရွက်မှုအဆင့်တွေ ဆက်သွားတယ်။

Booking status နဲ့ payment status က ဘာကွာသလဲ?

Booking status က အလုပ်၏တိုးတက်မှုကို ပြတယ်။ Payment status က ငွေတင်သွင်းမှု၊ စစ်ဆေးမှုနဲ့ refund ကို ပြတယ်။ နှစ်မျိုးကို သီးခြားစီ ထိန်းသိမ်းတာကြောင့် အလုပ်ပြီးပေမယ့် final payment စစ်ဆေးနေဆဲ ဖြစ်နိုင်တယ်။

Payment က ဘယ်လိုအတည်ပြုသလဲ? Online payment gateway ပါသလား?

လက်ရှိ code flow မှာ Customer က payment အချက်အလက်/slip တင်ပြီး Provider က verify သို့မဟုတ် reject လုပ်တဲ့ပုံစံကို တွေ့ရတယ်။ ပြင်ပ gateway/API တစ်ခုနဲ့ အလိုအလျောက်ငွေလွှဲခြင်းကို ဒီ project code မှာ အတည်ပြုမတွေ့ရဘူး။

Booking history ကို ဘယ်လိုစစ်ဆေးနိုင်သလဲ?

Status ပြောင်းတိုင်း သက်ဆိုင်ရာ history record ကို သိမ်းထားပြီး customer/provider view တွင် အခြေအနေကို ပြန်ကြည့်နိုင်တယ်။ Controller များက လက်ရှိ status ကို စစ်ပြီး ခွင့်ပြုသောအဆင့်အလိုက်သာ ပြောင်းခွင့်ပေးတယ်။

Database ကို ဘယ်လိုချိတ်ဆက်သလဲ?

Laravel database configuration ကို .env မှ ဖတ်တယ်။ Local machine ၏ connection အတိအကျကို project configuration က ဆုံးဖြတ်တာကြောင့် မိမိစက်ရှိ environment setting ကို စစ်ပြီးမှ ရှင်းပြသင့်တယ်။

Project မှာ ဘယ် architecture pattern ကို သုံးထားသလဲ?

Laravel ၏ MVC ပုံစံကို အခြေခံတယ်။ Route က Controller ကိုခေါ်တယ်၊ Controller က Model နဲ့ data/business rules ကို ကိုင်တွယ်ပြီး Blade View က ရလဒ်ကို ပြသတယ်။

Input ကို ဘယ်လိုစစ်ပြီး account ကို ကာကွယ်သလဲ?

Laravel validation ဖြင့် required field၊ email၊ password၊ ရှိပြီးသား ID စတဲ့အချက်တွေကို စစ်တယ်။ Password ကို hash လုပ်တယ်။ Authentication နှင့် role middleware တွေက ဝင်ရောက်ခွင့်ကို ထိန်းတယ်။

Transaction ကို ဘာကြောင့် သုံးသလဲ?

Booking တင်ရာမှာ Booking၊ Payment၊ history တို့က ဆက်စပ်နေတယ်။ တစ်ခုရေးပြီး နောက်တစ်ခုမအောင်မြင်လျှင် မပြည့်စုံတဲ့ data မကျန်စေရန် transaction ဖြင့် အစုလိုက်အပြုံလိုက် commit/rollback လုပ်တယ်။

Project ရဲ့ နောက်ထပ်တိုးတက်စေနိုင်သည့်အပိုင်းက ဘာလဲ?

Project အခြေအနေနှင့်လိုအပ်ချက်အပေါ်မူတည်ပြီး payment gateway၊ automated test coverage၊ audit/reporting၊ map/location UX၊ real-time message/notification တို့ကို နောက်ထပ်အဆင့်တွင် ထည့်စဉ်းစားနိုင်တယ်။ လက်ရှိရှိပြီးသား feature လို့ မပြောဘဲ အနာဂတ်တိုးချဲ့မှုအဖြစ် ရှင်းပြပါ။

၉။ ၁ မိနစ်ခန့် မိတ်ဆက်ပြောဆိုရန်

“ကျွန်တော့် project က QuickFix လို့ခေါ်တဲ့ service booking web application ဖြစ်ပါတယ်။ Customer တွေက ဝန်ဆောင်မှုအမျိုးအစားနဲ့ Provider ကိုရွေးပြီး လိပ်စာ၊ အချိန်နဲ့ လိုအပ်ချက်တွေထည့်ကာ booking တင်နိုင်ပါတယ်။ Provider တွေက Admin အတည်ပြုချက်ရပြီးမှ စနစ်ထဲဝင်ပြီး request ကို လက်ခံ/ငြင်းပယ်ကာ အလုပ်အဆင့်တွေကို update လုပ်နိုင်ပါတယ်။ Payment မှာ ကြိုတင်ငွေနဲ့ အလုပ်ပြီးနောက် နောက်ဆုံးငွေကို သီးခြားမှတ်တမ်းတင်ပြီး Provider က slip ကို စစ်ဆေးနိုင်ပါတယ်။ Customer နဲ့ Provider အတွက် dashboard၊ chat၊ notification၊ review တွေလည်း ပါဝင်ပါတယ်။ Admin က အသုံးပြုသူ၊ Provider approval၊ service နဲ့ တည်နေရာဆိုင်ရာ data တွေကို စီမံပါတယ်။ နည်းပညာအနေနဲ့ Laravel/PHP backend၊ Blade/JavaScript frontend နဲ့ relational database ကို အသုံးပြုထားပြီး role-based access နဲ့ validation တွေက လုပ်ဆောင်ချက်များကို ကာကွယ်ပေးပါတယ်။”
